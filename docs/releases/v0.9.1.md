## Upgrading from 0.9.0

No configuration change is needed, and nothing to review in `routr setup`: no setting is new or changed.

The update reinstalls routr's skills, and the orchestrator guide changed: it has a new "Unreadable" entry under
headless workers. An agent that already loaded routr reads the older guide until it rereads the skill or starts a new
session.

If you are upgrading from 0.8.3 or earlier, read [Upgrading from 0.8.3](https://github.com/sirkirby/routr/blob/main/docs/releases/v0.9.0.md#upgrading-from-083)
in the v0.9.0 notes first.

## Fixed

- **A headless worker file routr can't read is now treated as unknown, never as missing.** A headless worker keeps
  its record (`worker.json`), its state (`state.json`: session, turns, the process group its harness ran in) and the
  markers its process writes in its run folder. When one of them was there but couldn't be read (in use on Windows,
  half-written, or damaged), every routr command used to act as if it weren't there:
  - **A new worker process** (started by `routr send`) began from an empty state and wrote it over the real one,
    losing the worker's session and turns.
  - **`routr send`** said "no session to resume; launch the work again", and skipped its check that the harness had
    stopped.
  - **`routr cleanup --worker`** and **`routr stop`** skipped their check of the harness's process group.
  - **`routr workers`** showed the worker as `starting`, or left it out.
  - **`routr wait`** could stop waiting.

  Now:
  - no new worker process starts over a file it can't read;
  - `send`, `stop` and `cleanup --worker` refuse, with an error naming the file, though `stop` still stops a worker
    process that answers, and `send` still delivers to one when only the state file is unreadable;
  - `workers` shows `unreadable`, and `wait` keeps waiting.

  On Windows, a file another process is replacing is read again for up to 100 ms first. If a file stays unreadable,
  it's damaged, and each refusal's next step says what to do: make sure nothing of the worker still runs, finish its
  worktree, keep what you need, and remove its run folder yourself.
- `worker.json`, and the file `wait` uses to remember what it has already reported, are now written whole, so another
  command never reads them half-written.

## Verification

- `bun test` on macOS, Linux and Windows. A new test breaks each worker file of a real fixture worker in turn, and
  checks `workers`, `wait`, `send`, `stop`, `cleanup --worker` and a new worker process against each. It fails on
  0.9.0 and passes on 0.9.1. A unit test covers the reader's Windows retry, with a controlled clock.
- Review: an independent review by a routr worker on another model family, and three verification rounds; all
  findings were fixed.
- Not measured: a file damaged on a real machine (the tests write broken files); on Windows, a file missing for a
  moment (rather than unreadable) after the writer's retry has given up, which still reads as missing.

## CLI and JSON compatibility

No field or flag was removed or renamed.
- **`workers` and `wait`:** a worker entry's `state` can be `unreadable`. When its `worker.json` is unreadable,
  `kind`, `model`, `effort` and `cwd` are null.
- **`stop`:** `state` is `unknown` also when the worker isn't running and its record or state can't be read.
- **`send`, `stop` and `cleanup --worker`:** new refusals, whose message names the file, with a next step for a file
  that stays unreadable.
