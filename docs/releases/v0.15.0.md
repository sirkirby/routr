## More than one account of Claude Code or Codex

routr can now use more than one account of Claude Code or of Codex on one machine: a personal plan and a work seat, for example. Each account is a subscription of its own, named `<harness>-<name>` (`claude-work`, `codex-work`). It is checked for sign-in, read for usage, ranked by `dispatch` and `usage`, launched and recorded by that name.

An account is a folder: the one its harness keeps a login in. routr starts the harness with that folder in the harness's own variable (`CLAUDE_CONFIG_DIR` for Claude Code, `CODEX_HOME` for Codex), and never copies or reads the login itself. Cursor, Antigravity and Kiro have no such folder setting that routr knows, so they stay one account each.

**Add one in `routr setup`.** Choose Subscriptions, then "+ Add another Claude Code account" (or Codex). Setup asks a name and suggests a folder (`~/.claude-work`). If that folder is not signed in, setup offers to run the harness's own sign-in there and then, in your terminal, and carries on when it ends. For Claude Code it then offers to open it once in the new folder, because a new folder asks first-run questions that a worker would stop at. A first run of setup asks whether you have another account after it has asked each subscription's settings.

**Or by flag**, for a folder that is already signed in: `routr setup --account claude-work=~/.claude-work`. A flag run never starts a sign-in: it refuses, and says what to run.

**Its settings.** An account starts with its harness's settings, and follows them until you give it its own. On and off is the exception: an account is turned on or off by itself, so turning its harness off leaves the account on. The flags `--model`, `--effort`, `--hardest`, `--reserve`, `--use`, `--share`, `--enable` and `--disable` all take an account's name. In the config it is `subscriptions.<harness>.accounts.<name>`, written as its folder, or as `{ "folder": …, …settings }` once it has a setting of its own.

**Removing one.** "Remove this account from routr" in setup's list, or `routr setup --remove-account claude-work`. Its entry goes. Its folder, its sign-in and the routr skills linked there stay.

Things to know:

- **The same login is ranked once.** If your harness's default folder and an account's folder are the same login, routr ranks the account and leaves the harness's own entry out, saying why. The same account signed in from two different folders is not detected: it is ranked twice.
- **routr's skills are linked into a Claude Code account's folder**, as they are into `~/.claude`. A Codex account needs no link: Codex reads the shared `~/.agents/skills` folder.
- **A harness's models are listed once**, for the harness. An account on a different plan may refuse a model its harness lists.
- **A sign-in is only ever started by guided setup**, for an account you are adding or have listed there, when you say yes. No other command and no agent's `--yes` run starts one.
- **What a sign-in wrote stays.** The folder and the login the harness made there stay whether or not you save your settings, and setup says it ran a sign-in however the run ends: saved, left without saving, or stopped with Ctrl+C.

## `routr launch --subscription` replaces `--kind`

`routr launch` now takes `--subscription <name>`: the name `dispatch` ranks and `record` takes, which is a harness (`claude`) or an account (`claude-work`). **`--kind` is gone**: a launch that passes it fails with "Unknown launch option: --kind". The guides and every `next` step routr prints use the new flag. The update reinstalls the skills, but an agent that loaded routr before the update still has the old guide until it reads it again or starts a new session.

## Naming rework, and seeing it repeat

- **`routr record --cause-detail <tag>`** names what kind of extra work a run took, in your own words (`copied-existing-code`), beside a cause other than `none`. Tags are lowercase with hyphens and repeatable.
- **`record` points out a repeat.** When another run in the same project carried the same tag within the last 7 days, the first step in `next` says so. A revision of a run is reminded only of a tag it adds. `cause_repeat_days` in the config changes the window, and 0 turns it off. It is advice, and never fails a record.
- **`routr assess` lists the tags by project**, and counts a run recorded with no cause as "not recorded". Before, those runs were counted as `unknown`.
- **Launch's record template asks for `--cause`**, and a revision's template keeps the run's causes and tags.
- **Tags stay on your machine.** Telemetry, `routr share`, OpenTelemetry export, `board`, `top` and `dash` carry none.

## Guides

- The worker guide adds a `REUSED:` line to the report, and a last self-check before reporting.
- The orchestrator guide asks a brief to name the existing code the work must call rather than copy, to be checked against briefs still running, and asks the lead to check a brief's claims about the code before launch.

Neither change is measured: no test shows that they reduce rework.

## Upgrading from 0.14

- **Agents and scripts that call `routr launch --kind`** must pass `--subscription` instead. An agent picks this up from the reinstalled guide in a new session.
- **Your settings do not change**, and no setup is required. Running `routr setup` after upgrading is the place to add a second account (choose Subscriptions) and to review your choices: it keeps every setting you do not change.
- If you already keep a second login in a folder of its own, give setup that folder when it asks: it finds it signed in and asks nothing more about sign-in.
- Launch's record template now includes `--cause`. A lead following an older template still records, and `assess` counts that run as "not recorded".

## JSON and output changes

- `launch`: `--subscription` is required where `--kind` was. `kind` in the answer is still the harness. For an account, `start.env` shows the folder variable as `"<forwarded>"`, or `null` where routr removes it (Claude Code's `~/.claude`).
- `launch` refuses, for an account: `--pane` (an existing pane keeps its own shell's environment), and advice whose `dispatch` ranked that name from another folder.
- `dispatch`, `usage`: a `subscription` may be an account's name. A harness's own entry that is the same login as one of its accounts has no reading and is in `subscriptions.excluded`, with a `why` naming the account.
- `dispatch`: with accounts in the config, `accounts` gives each one's folder as a 12-character fingerprint, never the path. `launch` reads it.
- `doctor`: `accounts`, by name, with `harness` and `signed_in`; `sign_in` when it is not signed in; `usage` when its harness is installed; and `usage_stale` when a signed-in account's usage reader has stopped working. An account whose harness is not installed is listed with `signed_in: false` and a `sign_in` saying its command was not found.
- `setup`: `--account <harness>-<name>=<folder>` and `--remove-account <harness>-<name>`. The setting flags accept an account's name.
- `record`: `--cause-detail`, stored as `outcome.cause_details`. `--subscription` takes an account's name.
- `assess`: runs with no cause are counted as "not recorded", apart from `unknown`. Tags are listed by project.
- Config: `subscriptions.<harness>.accounts`, and `cause_repeat_days` (default 7).
- Telemetry sends an account as its harness (`claude-work` as `claude`): the account's name and folder are never sent. OpenTelemetry export sends a harness's name or `other`, and no usage reading of an account.

## How much of this was run

- **Two accounts each of Claude Code and Codex, live on macOS** (Claude Code 2.1.322, codex-cli 0.167.0; a personal plan and a metered work seat of each):
  - Usage read for all four, and the same-login entry left out.
  - One worker on each work account, in a Herdr app tab and in a herdr pane. Each worker's session files were under its account's folder only.
  - `smoke:usage` passes on the released code with all four accounts. `smoke:carriers` passed inside a live herdr session on the code of the first account change, before the setup changes, which do not touch a worker's environment.
- **Guided setup, by hand** (the sign-in runs on the code before the last round of setup fixes; the accessible-mode run on the code after it):
  - **macOS:** adding a Claude Code account and a Codex account from the Subscriptions list. The harness's sign-in ran inside setup, and Ctrl+C in it returned to setup with nothing added. Accessible mode (`ACCESSIBLE=1`) stopped with its summary at Ctrl+C.
  - **Windows 11** (Claude Code 2.1.308): a first run, adding an account, the sign-in inside setup, Ctrl+C back to setup, a second account from a folder already signed in, and saving.
- **A release-style binary built from a clean clone**, in a throwaway home with no harness installed: the skills installed and linked into a Claude Code account's folder, `doctor` listed the account with its harness not found, `--remove-account` took it out, `--account` refused, and `launch --kind` failed as described.
- **Not run live:** a sign-in completed through setup on a new account, and Claude Code's first-run opening after it. Codex on Windows, and anything on Linux beyond the tests. The repeat reminder and the tags were run by hand in a throwaway home, not on a real ledger.
- **Not measured:** whether the guide changes reduce rework.
