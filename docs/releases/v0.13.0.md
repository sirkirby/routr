## `routr top`: what routr knows, kept current beside your lead

Split a pane beside your lead (a split in the Herdr app, a herdr pane, or any terminal) and run `routr top` in your project, or `routr top --cwd <folder>` for another one. It draws three things and reads them again every 5 seconds:

- **Room:** each account's usable share, when its tightest window resets, and whether the account is a fallback or its reading is assumed or old. Accounts that are off or not signed in are listed too.
- **Decisions:** each launch's advised level, the level chosen when it differs, the account, model and effort, its age, and how it turned out. Press Enter for one decision's detail.
- **The last 7 days:** launches, recorded runs, done first time, level changed, check failed. A count routr cannot read shows as `?`, never 0.

Keys: up/down or j/k pick a decision, Enter opens it and Esc closes it, `a` switches between this project and all projects, `u` reads usage now, `q` quits. Nothing in `top` acts on a worker. From 120 columns Room and Decisions sit side by side; narrower, one above the other.

Piped, it prints one plain snapshot. With `ACCESSIBLE=1` or `TERM=dumb` it prints a plain snapshot for each line you type.

**While it is open it reads usage for you.** When the newest kept reading is over 10 minutes old, or one is missing, `top` starts one `routr usage` in the background, at most once per 10 minutes. That is the same read `routr usage` makes, through each harness's own CLI. Drawing the screen calls no harness.

## `routr board`: the same answer for an agent

`routr board [--cwd <folder>]` prints as JSON what `top` draws: `subscriptions` (exactly `routr usage`'s ranking), `decisions` (newest first, at most 50), and `outcomes` over 7 days. It calls no harness and answers within milliseconds, because it reads what earlier commands kept. An unreadable ledger or launch history is said in `unavailable`, and its counts are null, never zero.

## Each launch has one id

`routr launch` now returns a `launch_id`, and its record template passes it as `record --launch`. Keep it when you follow the template. The ledger row then belongs to the repository the worker was in, wherever you record from, and `board` and `top` can join the launch to its outcome. A run recorded before this release joins only when exactly one launch in the history used its advice.

## `routr workers` knows when a tab has gone

In the Herdr app, `routr workers` used to show a worker from its record alone, so a closed tab still looked live. It now asks `hc` and says `in_terminal`, `finished`, `gone`, or `unknown` with a `why`. For a finished or gone worker, `next` gives `routr cleanup --worker <name>`. Use that rather than removing its worktree by hand: otherwise its record stays and routr keeps listing it.

`routr cleanup --worker` reads the terminal the same way, which makes it stricter in one case. When `hc` refuses for any reason other than "no such terminal", cleanup now keeps everything and says so. In 0.12.0 such a refusal could count as a gone terminal when the worker's process had ended, and cleanup went on.

## New on your machine

Both stay on this machine, and telemetry sends neither.

- **`~/.cache/routr/usage-readings.json`:** each subscription's last good usage reading, written by every live read (`dispatch`, `usage`, `doctor`, `setup`). It holds the reading's source and time, how long it may be trusted, and its windows, class and note as the harness reported them, never a brief. An entry stays until a newer reading replaces it or routr's cache folder is removed.
- **Launch records carry more.** Each record under `~/.local/state/routr/launch-counts` used to hold the subscription and the time. It now also holds the model and effort chosen, the advice's id and reading, the project (the repository's folder name), where the worker runs, and its name. It never holds the task, the brief, a path, a note or a key. Older records still count. As before, a record older than 7 days is ignored and is removed by the next launch's write.

## Upgrading from 0.12.0

No setup is needed, and your settings do not change. The update reinstalls routr's skills, and the orchestrator guide changed its record step and its Herdr app section. An agent that already loaded routr reads the older guide until it reads it again or starts a new session.

`board` and `top` have history from the start. Runs already in your ledger appear as decisions at once, older than 7 days included, up to the 50 newest. Launch records from before this release hold no project, so they appear only when showing all projects, with their account and time and nothing else. Room fills after the first usage read, which `board` or `top` starts for you.

## How much of this was run

Measured on macOS:

- **`routr top` in a real terminal:** a compiled build from a clean clone, with a throwaway home and a fake harness, in a pseudo-terminal and in a real herdr-core terminal (hc 0.1.18). The alternate screen, the first draw, a detail, `u` and `q` worked, and the screen was restored on exit with code 0. The background read on opening and the one from `u` each reached the harness's usage command. Picking a decision, Esc and `a` ran against a real ledger when `top` was built, from source. It has not run as a split in the Herdr app itself.
- **`routr workers`:** the same build with a fake harness in real hc terminals: `in_terminal` while it ran, `finished` after `hc kill`, `gone` after `hc rm`, and `routr cleanup --worker` then removed the record. `unknown` is covered by tests only.
- **`launch_id`:** four real Codex workers in herdr panes, launched and recorded on this repository, each joined to its outcome in `routr board`. In a herdr-core terminal, the id was seen only with a fake harness; a headless launch is covered by tests only.
- **Usage reads:** `bun run smoke:usage` read Claude Code, Codex, Cursor and Antigravity live. Kiro is turned off on this machine and was not read.
- **OpenTelemetry:** `bun run smoke:otel` passed with fixture harnesses.

Not run: `routr top` in a real Windows console or Linux terminal (the tests drive it on all three systems with fake streams), `routr workers` on a tab closed by hand or with a real harness, a long-lived `top`. Whether seeing this view changes how anyone chooses models is not measured.

## JSON and output changes

These are additions, except for three changes to what was there: a terminal worker's `state` in `workers`, a revision's project in `record`, and `routr.launch.id` in OpenTelemetry. Each is below.

- New commands: `board` (JSON) and `top` (text for a person). Both take `--cwd <folder>`.
- `launch`: new `launch_id`, a UUID or null, on every backend. Its record template carries `--launch`.
- `record`: new `--launch <launch_id>`, and the row stores `launch_id`. The row's project is now `--project`; on a revision, the run's own; else the launch's; else the folder's. A launch made with other advice is refused, and so is a revision naming a different launch. A revision without `--project` now keeps its run's project, even without `--launch`; it used to take the current folder's, and could be refused when made from elsewhere.
- `workers`: a terminal worker's `state` can now be `finished`, `gone` or `unknown` as well as `in_terminal`; it was always `in_terminal`. It adds `status`, and `why` when unknown. Anything reading this field needs to expect the new values.
- New warning codes: `launch_not_found`, `launch_history_unreadable`, `headroom_unused`. New usage failure code: `not_read_yet`.
- The ledger: a line that is valid JSON but not an object (`null`, a number, a list: a hand edit) is now skipped, like one that does not parse. It used to reach every reader of the ledger.
- OpenTelemetry: `routr.launch.id` is now the same id as a launch's `launch_id`, whenever that is not null. A sampled dry run or failed launch answers `launch_id: null`, and its span still has an id. A `--pane` recovery rerun has its own id and links to the launch it finishes; it used to reuse the original's. A record span links by the `launch_id` its row names, before falling back to the advice id. `docs/opentelemetry.md` has the details.
