## Upgrading from 0.6.1

No configuration change is needed. Your settings file is read as before: a single `decision` model is read as a list
of one, and your subscriptions, models, effort, reserves, `fallback_level`, `sure_at` and update channel are preserved.

We recommend running `routr setup` once after upgrading and choosing "Decision model" from its menu, which now lets
you add a backup decision model. An agent can do the same with
`routr setup --yes --decision typesafe,cloudflare:clef` (the models you choose, first choice first). A backup needs its
own key: `routr key set cloudflare` for Clef on Workers AI; Ollama needs none.

The update reinstalls routr's skills, and the guides changed in this release. Ask an agent that already loaded routr
to reread the skill, or start a new session. The binary and the guides update together, so a lead that rereads the
skill needs nothing else. Scripts of your own that read routr's JSON need the changes under
[CLI and JSON compatibility](#cli-and-json-compatibility).

## Highlights

- **Every handoff is advised.** `routr launch` refuses to send a task without advice on that exact task, reviews
  included, so a long-running lead can no longer skip `routr dispatch` and launch at a model it fixed for itself. The
  account, model and effort stay the lead's choice; dispatch always answers, with fallback advice when its decision
  model cannot. Your reserves and level limits are applied in dispatch, so a launch can no longer skip them. `record`
  refuses advice given on another task, so the ledger cannot claim advice a worker never got.
- **Every command says the same five things the same way.** Each command a lead reads returns `ok` (did it work),
  `headline` (what happened), `unavailable` (what routr could not read, and why), `warnings` (what to know) and
  `next` (what to do next), with `error` only when `ok` is false. What to do is only ever in `next`: exact commands that
  run unchanged in bash, PowerShell and cmd, or instructions with a template. For example, a worker's folder-trust
  question now carries the guide's trust rule, and `record`'s next step depends on the outcome you recorded.
- **routr says what it could not read.** When the decision model could not answer, the headline says so first, and
  `unavailable` names the model it tried, the reason and the fix (for a missing key, where to get one). A usage
  reading routr could not make now is listed with the reading it kept and its age.
- **Name a backup decision model.** `decision` is now an ordered list. routr asks each model in turn and the first one
  that answers gives the reading; only when none can answer does it use your `fallback_level`.
  - It moves on when a model cannot answer right now: a timeout, unreachable, a provider error, no key, a used-up
    daily allowance, or a local model this machine cannot run or has not pulled. A refused key or a reply routr cannot
    read stops there and is reported, because those are yours to fix.
  - A hosted model is cut at 8 s and the whole reading keeps one deadline. A local model is asked after every hosted
    one, because it may need to load.
  - A backup's reading is ordinary advice, read with that model's own measured profile. The headline names the model
    that answered, `unavailable` lists each earlier model that could not answer, and `next` says to tell the user.
  - `routr doctor` tests every entry and says which are ready. `routr key set` saves a key and, if that provider is not
    in your list, gives the setup command that adds it; it never changes your settings itself.
- **Outside text stays out.** A decision model's reply, and herdr's and git's output, are classified where routr reads
  them into a fixed set of messages. Their text never reaches routr's output, your ledger or telemetry, except a
  worker's screen shown to the lead when the worker needs input.
- **[docs/guarantees.md](https://github.com/sirkirby/routr/blob/main/docs/guarantees.md)** lists what routr reads,
  writes, starts and removes on your machine, and the limits that remain. **CHANGELOG.md** now keeps a one-line
  history of each release, linked to these notes.

## Verification

Measured (recorded in [docs/evidence.md](https://github.com/sirkirby/routr/blob/main/docs/evidence.md)):
- **Why a backup model:** on the model gate's 104 labelled briefs (2026-10-18), Clef on Workers AI read the level
  exactly 72 times against 58 for the default constant fallback (`standard`), with 6 under-ratings against 22; on 36
  real runs, 26 against 21. Jev, the default first choice, read 83.

Checked for this release:
- **Is the output useful?** Fresh Claude Code and Codex leads were each given only routr's skill and one real output,
  in seven situations: a normal dispatch, the decision model down, every account at its reserve, a launch without
  advice, a worker's startup question, a refused cleanup and a record revision. After three fixes, all 14 did what the
  output said.
- **Reviews:** each change was reviewed by a routr worker on another model family, which drove the CLI against fake
  herdr, git and decision providers that plant marker text. No marker reached output or the ledger. The
  reviews of the output contracts and the decision list broke the code on purpose 34 times, and every breakage now
  fails a test.
- **Tests:** `bun test` on macOS, Linux and Windows, including the bash, PowerShell 5.1/7 and cmd command tests.

Not measured:
- How often a decision provider is down in real use, and so how often a backup answers.
- Jev 1.14: its gate on 2026-10-18 and two repeat gates on 2026-10-19 held the pin at 1.13.0. Fact readings were
  less stable across repeats than on 1.13.0 in every run.

## CLI and JSON compatibility

**Renamed and removed output fields** (no old name is kept beside its new one):

| now | was |
|---|---|
| `ran`, `would_run` | `command`, `planned_command` |
| `start.executable`, `start.argv`, `start.env` | `argv`, `env` |
| `screen` | `needs_input.screen`, `pane_text` |
| `id` (record: the advice's id, beside `run_id` and `ledger`) | `recorded` |
| `subscriptions.*` in `usage` | top-level fields |
| `excluded[].why` | `excluded[].reason` |
| `warnings` | `config_notes`, `input_notes`, `warning` |
| `next` (a list of `run` and `do` steps) | launch's `cleanup` and `needs_input.then`, cleanup's `then` and `refused.then`, `check`'s single `next` |
| removed | `fallback`, `rule`, `refused`, `how`, `read_yourself` |

New on every command a lead reads: `ok`, `headline`, `unavailable`, `warnings`, `next`. Fallback advice is now read
from a `decision model` entry in `unavailable`, not a `fallback` flag.

**Commands:**
- `routr launch` needs `--advice` on the exact task (`--dry-run` without it plans, returns `ok: false` and exits 1);
  `--trust` is gone and is refused as an unknown option.
- `dispatch` and `subagent` take `--task-file`; task and advice files may be UTF-8 (with or without a byte-order mark)
  or UTF-16, as PowerShell saves them.
- `record` needs `--subscription`, `--model`, `--effort`, `--verdict` and `--check`; with `--task-file` it refuses
  advice given on another task. `--run-id` takes a run's `run_id`, not the advice `id`.
- `check` needs `--brief` and `--report`. An empty brief is a JSON refusal (exit 0; it was exit 2).
- `routr setup --decision` takes a comma-separated ordered list; `routr key set` with no provider uses the first entry
  that needs a key.

**Config:** `decision` may be a list of `{ "provider", "model" }`; a single object is still read. Bad or duplicate
entries are dropped with a warning whose setup command repairs the file.

**Saved advice and the ledger:** advice saved by 0.6.1 is still read by `launch` and `record`; a saved refusal is
refused. Ledger rows record the provider and model that answered, and a backup's reading is not marked as fallback.

**Telemetry:** unchanged, and off unless you turned it on.
